# Lost Batalion — CLAUDE.md

Real-time strategy (RTS) game built with **libGDX**. Player commands an army,
builds bases, gathers resources, develops tactics to beat an opponent. Emphasis
on terrain, positioning, line-of-sight and formations over raw army size.

> Design pillars (from the brief): strategic planning, reading the battlefield,
> reacting to change, weighing alternatives. Terrain and visibility are
> first-class mechanics, not decoration.

Most in-code comments and commit messages are in **Ukrainian**. Match that when
editing existing comments; new code comments may be English or Ukrainian.

## ⚠️ Repo layout gotcha

The Gradle project root is **`main/`**, NOT the repo root. The repo root
(`E:\GitReps\Lost-Batalion`) contains only `main/` plus IDE files.

- Run all Gradle commands from `main/`: `cd main && ./gradlew <task>`
- `settings.gradle`, `gradlew`, `assets/`, and all modules live under `main/`.

## Stack

- **Engine:** libGDX `1.14.0`
- **Language:** Java, `sourceCompatibility = 21` (desktop compiles with `release 21`; Android module uses Java 17). Було 23 — знижено 2026-08-03, бо жодної мовної фічі понад 21 у коді немає, а 23 вимагав рідкісний JDK і ламав construo-бандли під Linux/macOS (вони несуть JRE 21). Не піднімати назад без реальної потреби.
- **Build:** Gradle (wrapper included), Android plugin `8.9.3`
- **Extra libGDX deps declared** (mostly unused so far): ashley `1.7.4` (ECS), gdx-ai `1.8.2`, gdx-box2d, gdx-freetype
- **Packaging:** construo `2.1.0` (native bundles + jlink per-OS); optional GraalVM native image (`enableGraalNative=false`)

> ⚠️ ashley (ECS) and gdx-box2d are on the classpath but the game does **not**
> use an entity-component-system or Box2D physics. Units are plain OOP classes
> (`Unit` hierarchy) with hand-rolled movement/combat. Don't assume ECS.

## Modules (`main/settings.gradle`: `lwjgl3, android, server, core`)

- **`core`** — all shared game logic. Where nearly all work happens.
- **`lwjgl3`** — desktop launcher (LWJGL3). Primary run target.
- **`android`** — Android launcher. Needs Android SDK.
- **`server`** — standalone stub, no access to `core`. Not wired into gameplay.

Base package: `io.jababa.lost_batalion`

## Run / build (from `main/`)

- `./gradlew lwjgl3:run` — launch desktop game
- `./gradlew lwjgl3:jar` — runnable jar → `lwjgl3/build/libs`
- `./gradlew build` — build everything
- `./gradlew server:run` — run server stub
- **No tests exist** (`src/test` absent). `./gradlew test` is a no-op.

> ⚠️ **Ніколи `./gradlew build`** — воно тягне модуль `:android`, якому потрібен
> Android SDK (його тут немає), і падає. Завжди конкретні задачі: `:lwjgl3:jar`,
> `:lwjgl3:packageWinX64` тощо. Конфігурація `:android` без SDK проходить, тому
> решта модулів збирається нормально.

### CI (`.github/workflows/build.yml`)

Кожен push збирає гру й дає завантажуваний файл. Три групи задач:

- **`jar`** — `:lwjgl3:jar`, найшвидший сигнал, що код компілюється.
- **`bundles`** — матриця з 4 нативних бандлів (`packageWinX64`, `packageLinuxX64`,
  `packageMacX64`, `packageMacM1`) з ОДНОГО Linux-раннера: construo сам качає JDK
  цільової платформи, тож крос-збірка працює (перевірено — Linux-бандл зібрано на
  Windows). `fail-fast: false`, щоб зламаний таргет не забирав решту.
- **`release`** — лише з `main`: перекладає преліз `latest` на свіжий коміт.
  Артефакти Actions живуть 30 днів і вимагають входу; реліз дає постійне публічне
  посилання.

Пастки, вже обійдені — не «спрощувати» назад:
- `main/gradlew` мусить лишатись **виконуваним у git** (`100755`). Був `100644`,
  і на Linux-раннері не запускався б; у workflow ще й `chmod` про всяк випадок.
- Кеш JDK для construo ключований по `main/lwjgl3/build.gradle` — там лежать
  `jdkUrl`, і без цього кожен прогін качав би ~760 МБ.
- Робоча тека всіх кроків — `main/`, а не корінь репозиторію.

Вихід збірки: `main/lwjgl3/build/libs/*.jar` і
`main/lwjgl3/build/construo/dist/<appName>-<таргет>.zip`.

### Скріншоти (`debug/`)

Єдиний спосіб для того, хто не сидить перед монітором, побачити, як гра
СПРАВДІ виглядає. До появи цього все про вигляд перевірялось реконструкціями
в PIL, а вони не відтворюють ні метрик шрифту libGDX, ні `NinePatch`, ні `Table`.

- **`F12`** — знімок у `~/LostBatalion/screenshots/` (глобально, поряд із `F11`;
  повний шлях друкується в лог тегом `SCREENSHOT`).
- Типова тека — **домашня, а не проєктна, і це важливо**: робоча тека процесу при
  запуску через Gradle — `main/assets/`, тож `Gdx.files.local` складав знімки прямо
  в асети, звідки їх забирав `generateAssetList` і пакував у jar. Тому в
  `Screenshot.resolve` стоїть `Gdx.files.external`. Не міняти назад на `local`.
- **Режим «запустись, знімись, закрийся»** — системні властивості, не налаштування:

```bash
java -Dlb.shotAt=2,5 -Dlb.autoMatch=true -Dlb.shotExit=true \
     -Dlb.shotDir=<куди> -jar "lwjgl3/build/libs/Lost Batalion-1.0.0.jar"
```

| властивість | що робить |
|---|---|
| `lb.shotAt=2,5` | секунди від старту; вмикає весь режим (без неї нічого не діє) |
| `lb.autoMatch=true` | одразу в матч повз меню — інакше знімок покаже лише головне меню |
| `lb.shotExit=true` | вийти після останнього знімка |
| `lb.shotDir` | тека (абсолютна або відносна); типово `screenshots/` |
| `lb.scenario` | id карти; типово перша з `ScenarioCatalog` |
| `lb.screen=scenario\|settings\|multiplayer\|lobby\|lobbyguest` | відкрити меню-екран одразу; те саме призначення, що й `autoMatch`, але для меню — інакше автознімок бачить лише головний екран |
| `lb.joinAddress`, `lb.nick` | куди й під яким ніком під'єднується `lobbyguest`; типово `127.0.0.1` / «ГІСТЬ» |
| `lb.autoStart=true\|<N>` | хост тисне «Старт»: `true` — щойно можна, ЧИСЛО — щойно в складі стільки-то учасників. Число потрібне тому, що з ботом-суперником умови старту виконуються негайно, і хост зривається в матч раніше, ніж під'єднається живий гість |
| `lb.autoSeat=команда:місце` | гість сідає й підтверджує готовність — ті самі два виклики, що клік по вільному рядку й «Готовий» |
| `lb.lobbyBots=<N>` | скільки ботів садити в дев-кімнаті (типово 3, нуль — жодного). Перший бот завжди суперник |
| `lb.devCmd="..."` | сценарій дев-консолі на старті матчу, розділювач `;` (див. розділ про консоль) |

**Лоббі знімається ДВОМА процесами.** Половина екрана кімнати існує лише в
гостя (кнопка «Готовий» замість «Старт», відсутність хостових дій у рядках), і
побачити її з боку хоста неможливо в принципі. Тому `lb.screen=lobby` піднімає
справжню кімнату й садить у неї ботів ТИМИ Ж публічними викликами, що й людина
кнопками, а `lb.screen=lobbyguest` другим процесом заходить у неї по loopback.
Обидві гілки нічого не підробляють у стані: знімок мусить показувати розкладку,
яку гра вміє виробляти.

> Процес із піднятою кімнатою **не завершується сам** навіть із `lb.shotExit`:
> потоки KryoNet не демонські, і JVM живе далі. Знімальний прогін треба вбивати
> ззовні, інакше наступний не займе порт 54555.

Дві пастки, вже обійдені в `Screenshot.capture`, — не «спрощувати» назад:
**flipY** (OpenGL віддає рядки знизу вгору) і **альфа з буфера приходить нульовою**,
тож канал забивається `0xFF` вручну — без цього PNG виходить цілком прозорим.
Знімається саме кадровий буфер, тобто з HUD, bloom і туманом війни.

## Architecture

`LostBatalion extends Game` (entrypoint) → `Screen` per state:
`MainMenuScreen` → `ScenarioScreen` → `GameScreen` (+ `SettingsScreen`).
`BaseScreen` is the shared scene2d-Stage base for menu screens.

Input: global `InputMultiplexer` in `LostBatalion`; each screen swaps processor 1
via `game.setScreenInputProcessor(...)`. F11 toggles fullscreen globally.

### GameScreen — the core loop
`core/.../screens/game/GameScreen.java` orchestrates everything: camera
(`OrthographicCamera` + `ExtendViewport` 900×580), map texture, and per-frame
`update`/`render` of all subsystems. It builds an `InputMultiplexer` that differs
for desktop (mouse/keyboard `buildGameInput`) vs mobile (`MobileTouchHandler` +
`GestureDetector`/`GameInputHandler`).

Map size = map texture size. World coords are pixel coords (Y-up); terrain masks
are sampled with Y flipped (`height-1-y`).

### Units (`units/`)
- `Unit` (abstract): hp/maxHp, speed, damage, attackRange, attackCooldown,
  `defense` (flat armor), `sightRange`, `stealthRating`, `visibleToPlayer`,
  position/target, `moving`, `selected`, `alive`. Linear `moveTo` movement (no
  pathfinding). `takeDamage` / `takeDamageWithTerrain` (armor then terrain
  multiplier). `attack` / `attackWithTerrain`.
- `Infantry` — hp100, dmg15, **range90**, defense3, stealth0.20, size10.
  Єдиний тип із РОЗКИДОМ: `hitChanceAt` дає 100% до 30 одиниць і лінійно падає
  до 35% на межі 90 (мушкет, а не гвинтівка). Промах їсть кулдаун
  (`consumeAttackCooldown`) і малює трасер повз ціль, але не завдає урону.
  Кидок робить `CombatManager.tryAttack` через `DeterministicRandom` — рівно
  один на постріл. Хто повертає `hitChanceAt == ONE` (усі інші), RNG **не
  смикає взагалі**: гілка залежить від класу юніта, тож однакова на всіх
  клієнтах. Було range40 — при огляді 520 це 13:1, і позиція не важила нічого.
- `Cavalry` — hp80, dmg26, range20 (впритул), defense2, speed40, cooldown 0.7 с,
  stealth0.10. Штовхає ціль (`knockbackForce`), не стріляє (`usesRangedFx=false`),
  єдина тремтить у бою (`combatShakeScale`).
- `Artillery` — hp180, defense5, size32. `damage=0`/`attackRange=0` on purpose:
  it does **not** use the normal attack path. Instead `CombatManager` drives it:
  aim (3s) → AoE strike (splash 45, dmg120, spread 18) → reload (8s), range 220.
  `manualTarget` (RMB on enemy) overrides auto-target while alive & in range.
  **splash 45 мусить лишатись більшим за 16** — це мінімальна відстань між
  юнітами (`UnitSeparation`, hitRadius 8+8). Колись тут стояло 15, і AoE-зброя
  за побудовою не діставала більш ніж одну ціль: разом із damage 50 і spread 24
  це давало 1.25 dps за 150 золота, тобто 80 секунд на одного піхотинця.
- `UnitManager` — owns `allUnits` + `selectedUnits`. Selection (click / shift /
  rect), formation moves (`moveSelectedTo` grid, `moveSelectedToLine`), dead-unit
  cleanup, per-frame update applying terrain speed multiplier.

### Combat (`units/CombatManager.java`)
Central combat brain, runs every frame. Handles:
- Auto-attack: each non-artillery unit attacks nearest **visible** enemy in range.
- Manual attack orders (`orderAttack`): forms a line facing the target
  (`AttackGroup` SPREAD→ADVANCE phase machine, `AttackOrder` per unit).
- Terrain-aware damage via `TerrainCombatModifier` (+ forest ×1.5 defense).
- Artillery special-cased separately (`updateArtillery`, `fireArtillery`,
  `applyArtilleryAoe` — AoE hits friendlies too, falloff by distance).
- Visual effects: `ShotEffect` pool (64), `ArtilleryStrikeEffect` (shell arc +
  `ExplosionAnimation`), `TargetPopupManager`, aim/reload bars, shot sound.

### Terrain (`terrain/`) — mask-driven
Two grayscale/colour PNG masks per scenario, sampled by pixel colour
(`TerrainMaskManager`, tolerance 20):
- **Forest mask** (`*_mask.png`): forest tiles (movement + LOS + stealth).
- **Terrain/topography mask** (`*_terrain_mask.png`): elevation + rivers.
- `TerrainType` enum: NONE, FOREST, RIVER, LOWLANDS/PRE_LOWLANDS (1a/1b),
  PLAINS/PLAINS_ALT (2a/2b), PRE_HIGHLANDS/HIGHLANDS (3a/3b), VILLAGE. RGB codes
  documented in `TerrainMaskManager`. VILLAGE (#F0FF00) лежить у масці **лісу**,
  як і річки, і на рух/бій не впливає — з нього будуються точки захоплення.
- `TerrainMovementModifier`: forest ×0.70, river ×0.40, hills ×0.85 (multiply).
- `TerrainCombatModifier`: defender defense multiplier by attacker-vs-defender
  elevation (high ground bonus, valley penalty). See table in that file.

### Топографія (`screens/renderer/TopographyOverlay`)
Оверлей ярусів висот на всю карту, перемикається клавішею **T** (WASD зайняті
камерою, ALT — оверлеєм огляду). Потрібен тому, що рельєф дає ±30% захисту і
змінює огляд у 3.25 раза, а на самій карті яруси майже не розрізняються —
вся математика працювала внаслі́пу.

Одна текстура розміром з карту, побудована ЛІНИВО при першому вмиканні
(1440×1440 ≈ 58 мс), далі просто малюється поверх карти з `ALPHA 0.45`.
Гіпсометрична шкала: низини зелені, височини руді, річки сині.
**Перевертень застосований при побудові** (рядок 0 пікмапи = найбільший
світовий Y), тому малюється БЕЗ від'ємної висоти — інакше оверлей ліг би
дзеркально до місцевості, яку описує. Фільтр `Nearest`: межі ярусів це східці
в масці, і згладжування домалювало б кольори неіснуючих ярусів.

Не плутати з `TerrainIndicatorRenderer` — той показує ярус під ВИДІЛЕНИМ
юнітом («де я стою»), а це «куди мені йти».

### Visibility / fog (`visibility/`)
- `VisibilitySystem` — recomputes `visibleToPlayer` for every enemy each frame.
  `effectiveSight = sightRange × sightMod(observer terrain)`; stealth from forest
  (target-in-forest ×1.8, forest-on-LOS-path ×4.0 via ray-march sampling) and
  elevation; detected if `dist ≤ effectiveSight × (1 − stealth)`.
- `FogOfWarRenderer` — draws fog; ALT held shows cursor sight overlay.
- Combat & rendering both respect `visibleToPlayer` (can't attack/see hidden enemies).

### Точки захоплення (`capture/`)
- Зони — **авторські дані сценарію** (`CaptureZone` у `ScenarioCard`), а НЕ
  похідні від маски. Кожна — опуклий чотирикутник (4 вершини у світових
  пікселях) плюс назва («A», «B», «C»), яку показує HUD. `CaptureManager`
  просто перекладає список у `CapturePoint`.
- Раніше точки виводились із плям VILLAGE (`findClusterCenters` + злиття <135),
  а зоною було коло r=70. Форма села ні на що не впливала: межа могла лежати
  посеред річки, а хутір із двох купок доводилось зливати порогом відстані.
- `CapturePoint.contains` — знак векторного добутку по 4 ребрах, цілочисельно.
  Обхід вершин будь-який; точка рівно на ребрі зараховується всередину.
  Чотирикутник МУСИТЬ бути опуклим, інакше перевірка бреше.
- Одна сторона в зоні → +2/тік (12 с на захоплення), обидві → прогрес завмирає,
  порожньо → −1/тік назад. Чужу точку спершу треба обнулити, потім набрати свою.
- Це стан симуляції: цілі числа, окремий компонент checksum (`C_POINTS`) і блок
  у `SimulationSnapshot`. Самі вершини в знімок не їдуть — вони константи.
- `screens/renderer/CapturePointRenderer` малює чотирикутник кольором того, хто
  ТЯГНЕ (`holder ?: owner`), і **мигає**, поки `0 < progress < FULL`.
  Проходу `BloomEffect` тут БІЛЬШЕ НЕМАЄ: світіння робило зону найяскравішим
  об'єктом кадру, у рази більшим за юніта. Звичайний альфа-блендинг, колір НЕ
  premultiplied. Той самий колір і той самий період мигання, що в літер у HUD.

### Лоббі на 5 на 5 (`net/messages`, `net/kryo`, `steam`) — з 2026-08-08

Протокол **8**. `MAX_PLAYERS = TEAM_COUNT × TEAM_SIZE` = 10 — стеля похідна від
розкладки, а не окреме число, яке колись із нею розійдеться.

- `PlayerSlot` несе `team` (0/1/`TEAM_NONE`), `seat` (0..4), `bot`,
  `botDifficulty` (**іменем константи**, не ordinal), `colorIndex`, `steamId`.
  Копіювання — ТІЛЬКИ через `PlayerSlot.copy()`: раніше воно було розкидане по
  трьох файлах і кожне нове поле треба було не забути в кожному.
- `LobbyState.slots` — лише ЗАЙНЯТІ місця (і команди, і список очікування
  `team == TEAM_NONE`). Закриті місця — маски `closedMask[team]`, по біту на
  місце: масив `boolean[][]` довелось би реєструвати в Kryo, а так це два числа.
- **Приєднання веде в СПИСОК ОЧІКУВАННЯ**, не в команду. Автопосадка була в
  проміжній версії й прибрана: сторону обирає гравець, інакше двоє друзів, що
  зайшли одночасно, опиняються по різні боки.
- **Хост — єдина влада, і гілка одна.** Гість шле повідомлення, хост викликає
  той самий метод напряму. Окремої «хостової» гілки з іншими правилами немає
  навмисно — саме так у першій версії лоббі й розходилось те, що бачить хост, і
  те, що в кімнаті насправді.
- Зайняте чи закрите місце — **не помилка, а гонка**: прохання просто не
  виконується. Закрити ЗАЙНЯТЕ місце не можна — це був би кік чужими руками.
- **Кік шле причину ДО розриву** (`KickPlayer`), інакше вигнаний бачить
  «зв'язок втрачено» і думає на свою мережу.
- **Автора чату підставляє хост** зі свого списку: присланому `playerId`
  довіряти не можна.
- **Глядач у матч не йде.** `StartMatch` везе лише тих, хто сидить
  (`copySeatedSlots`), а екран лоббі перевіряє власне місце перед переходом: у
  lockstep учасник без армії — це той, від кого решта чекає наказів.

**Steam — інша модель, і це не спрощується.** Хоста-роздавача там немає, обидві
сторони читають ті самі метадані:
- місце — ЧЛЕНСЬКІ дані (`lb_seat`), бо це вибір самого гравця; конфлікт двох
  охочих розв'язується ПРИ ЧИТАННІ (лишається менший номер), тож арбітраж не
  потрібен;
- закриті місця (`lb_closed`) і боти (`lb_bots`) — дані лоббі, пише лише
  власник; номери ботам роздаються після людей, за порядком рядка;
- кіку в Steam-лоббі НЕМАЄ як API — це оголошення (`lb_kick`), вигнаний виходить
  сам;
- **склад матчу їде в `lb_start` явно** (місця людей + боти). Дочитувати команди
  з членських даних при старті не можна: результат залежав би від того, коли
  Steam устиг реплікувати, а це різні армії при однакових наказах;
- хост МУСИТЬ писати собі `lb_seat = "0:0"` при створенні лоббі, інакше сидить у
  списку очікування й «Старт» не вмикається ніколи (набита ґуля).

**Екран кімнати описаний у [`DESIGN.md`](DESIGN.md) §10** — читай перед будь-якою
правкою `LobbyScreen`. Там же єдине в грі місце, де розкладку диктує розрахунок
ширини, а не смак: `Table` не вміє стиснути вміст нижче мінімуму, тож зайва
кнопка в рядку місця виштовхує бічні колонки за край екрана.

### Аватарки (`net/api/AvatarSource`, `steam/SteamAvatarSource`) — з 2026-08-08

Джерело аватарок належить **мережі**, а не екрану: `NetBackend.avatars()`. У
Steam картинка є, у локальній мережі її немає й узятись нізвідки — тому екран
питає мережу, а не перевіряє її назву. Типове значення — `AvatarSource.NONE`, а
не `null`: перевірка на порожнє джерело інакше розповзлась би по всіх місцях
малювання, а стан «аватарки немає» однаково потрібен для ботів.

- **`update()`, а не колбек, робить появу гарантованою.** Це виміряно, і саме
  тут була б тиха вада. Steam уміє дістати аватарку МОВЧКИ:
  `getMediumFriendAvatar` починає віддавати дескриптор, а
  `onAvatarImageLoaded` не приходить взагалі — так поводиться клієнт на
  «холодному» акаунті (зонд: аватарка з'явилась, `revision` лишився 0). Оскільки
  екран перепитує лише при зміні `revision`, гра назавжди застрягла б на літері
  при готовій картинці. Тому джерело саме опитує очікуване з кадрового такту
  бекенда. Колбек лишився як безкоштовне раннє пробудження.
- **Три стани, і кожному потрібне своє місце**: немає ніде — ще не питали; у
  `requested` — попросили, чекаємо; у `cache` — готово. Без набору «попросили»
  запит ішов би щокадру: рядки лоббі перебудовуються на кожне повідомлення від
  хоста.
- **Текстура народжується ТІЛЬКИ в `avatarFor`**, тобто в того, хто малює.
  `update()` і колбек GL не чіпають — лише знімають позначку й підіймають
  лічильник.
- **Steam кешує аватарки на диску**, тож той самий id холодний рівно один раз на
  машину. Зонд, який перевіряє асинхронний шлях, мусить ШУКАТИ невідомий акаунт,
  інакше після першого ж прогону він завжди тестує теплий кеш і нічого не ловить.
- Розмір — середній, 64×64. Малий (32) мулький уже в рядку лоббі, великий (184)
  — увосьмеро більше пікселів заради того, що стиснеться фільтром.
- **Текстурами володіє джерело**, і воно переживає і екран лоббі, і матч.
  Звільняє їх `MultiplayerServices.disposeAvatars()` з `LostBatalion.dispose()`,
  по ВСІХ бекендах: гравець міг перемкнути мережу посеред сеансу.
- `ui/AvatarBox` — квадратик учасника: аватарка, а поки її немає, перша літера
  ніка. Літера, а не порожня пластина, бо порожніх була б більшість (LAN, боти,
  перші кадри в Steam), і ряд однакових квадратів не розрізняє нікого. Той самий
  віджет у лоббі й у HUD матчу — плашка рахунку це scene2d, а не ручний батч.
- **Ніка й SteamID у ростері** (`PlayerRoster.nick/steamId`). На симуляцію вони
  не впливають ніяк і саме тому лежать там: другий список того самого набору
  гравців рано чи пізно розійшовся б із цим, а ростер і без того незмінний від
  старту й однаковий у всіх.
- **Кольори гравців — `UIFactory.playerColor(colorIndex)`**, десять різних за
  ВІДТІНКОМ. Це не кольори сторін: сторін дві, а гравців до п'яти на кожній, і
  розрізняти союзників синім і червоним неможливо. Індекс приїжджає з лоббі, тож
  тон однаковий у всіх, хто дивиться. **Одне джерело на все**: обводка аватарки
  в HUD і кільце навколо юніта беруть його звідси, інакше тон угорі й тон на
  полі розійшлись би для одного гравця.
- **Кільце власника — лише на СОЮЗНИХ юнітах** (`UnitRenderer.marksOwner`:
  `owner != я && roster.allied(owner, я)`). Свої й ворожі — без кільця; чому
  саме так, див. `DESIGN.md` §7. Союзного юніта неможливо ще й ВИДІЛИТИ
  (`UnitManager.collectOwned` фільтрує за owner), тож кільце і біла обводка
  виділення на одному юніті зійтись не можуть — звідси `else if` у рендері.
- `SteamAvatarSource` тримає **єдиний на процес `SteamFriends`** — його колбек
  потрібен саме аватаркам, тож ім'я персони (`defaultNick`) питається теж у
  нього, а не в другого екземпляра з тими самими підписками.

### Схованка трафіку матчу (`matchBacklog`) — з 2026-08-08

**Між `StartMatch` і створенням каналу матчу є ВІКНО, і в нього провалювались
пакети.** Лоббі-сесія бачить `StartMatch` у мережевому потоці й кладе подію в
чергу; розбирає її вже екран, у своєму `render`. Канал матчу
(`ClientMatchTransport` / `HostMatchTransport`) з'являється аж тоді. Усе, що
прилетіло раніше, дispatch-илось лише лоббі-слухачеві, який мовчки це ігнорував.

Наслідок — **матч, який не починається НІКОЛИ**, без єдиної помилки: гість
назавжди лишається на «Очікуємо суперника», хост показує «гравець гальмує матч».
Виміряно на двох живих клієнтах: хост надсилав розігрів на 19 мс раніше, ніж
гість реєстрував слухача.

- Обидві сесії складають нерозпізнані повідомлення в `matchBacklog`, а
  `openMatch` віддає їх новому транспортові через `replay(...)`.
- Хостова схованка тримає ще й **номер з'єднання**: автора хост визначає за ним,
  а не за полем у пакеті.
- Вікно є в ОБОХ: у гостя воно ширше (чекає TCP + кадр), у хоста вужче
  (`sendToAllTCP(start)` → кадр → `openMatch`), але швидкий гість у нього влучає.
- Дублікат при заміні нешкідливий і на нього покладаємось: `CommandBuffer.receive`
  бере лише перше повідомлення на пару (тік, гравець), книга хешів —
  `putIfAbsent`.

### Мережеві боти (`ai/BotPlayer`, `net/kryo/HostMatchTransport`) — з 2026-08-08

Бот у мережевому матчі — **такий самий учасник lockstep, як людина**: той самий
`TickCommands`, та сама затримка вводу, той самий буфер. Нового повідомлення й
нової версії протоколу етап не потребував узагалі — гість не відрізняє накази
бота від людських і не мусить.

- **Боти живуть у ТРАНСПОРТІ, а не в `MatchRunner`** (`MatchTransport.setBots`).
  Різниця між ботом і людиною лише в тому, ЗВІДКИ береться повідомлення, а це
  якраз справа каналу. `LocalMatchTransport` робив так від початку; тепер те
  саме вміють `HostMatchTransport` і `SteamMatchTransport`.
- **Рахує їх ЛИШЕ хост.** Не оптимізація, а вимога: два джерела наказів на один
  `playerId` дали б два різні повідомлення на той самий тік.
- **Повідомлення бота народжується разом із флешем локального гравця** і на той
  самий тік. Прив'язка до чужого флешу дає рівно одне повідомлення на тік без
  власного лічильника — і робить те саме для розігріву й для ресинку, бо обидва
  шлють свої порожні пакети тим самим шляхом. `setBots` тому й треба кликати ДО
  `new MatchRunner`: його конструктор одразу шле розігрів.
- **`BotPlayer.PLAYER_ID` більше не «номер бота взагалі».** Було константою 1, і
  це мовчки ламало все: обидва мережеві боти підписувались номером 1, тобто на
  місце наказів ГОСТЯ, а власних номерів не подавав жоден — матч не робив ані
  тіку. Тепер номер це поле екземпляра (`new BotPlayer(playerId, brain)`), а
  константа означає рівно склад одиночної гри. Симптом був би невидимий:
  «мережева гра з ботом не починається», без натяку на причину.
- **`MatchRunner.checksumPlayers` — окремий список без ботів.** Наказів від бота
  чекають нарівні з людськими, а хешів він не шле взагалі (він не окрема
  симуляція). `ChecksumLedger` порівнює лише коли комірка тіку зібрала ВСІХ зі
  списку — тобто один бот у складі тихо вимикав би виявлення десинхрону на весь
  матч. З тієї ж причини бот пропускається в `tryFinishResync`: підтвердження
  знімка від нього не буде ніколи.
- **Steam: `playerIds` беруться зі СКЛАДУ, а не з `lb_members`.** У метаданих
  лежать самі люди; бот, пропущений тут, означав би, що хост шле накази на
  номер, якого ніхто не чекає. Черга надлишковості (`redundancyBudget`) теж
  залежить від кількості ботів: за один тік хост шле `1 + ботів` пакетів, і при
  сталій межі в дві штуки дублювався б той самий тік замість двох попередніх.
- Рівень бота везе `PlayerRoster.botDifficulty` (**іменем константи**): мозки
  будуються вже після старту матчу, зі складу, а слотів на той момент немає.
- Перевірено стендом «хост + гість через 127.0.0.1, у складі 2 людини + 2 боти»:
  600 тіків без зупинок і без десинку, боти виставили по 11 юнітів, підкинута
  розбіжність стану ловиться звіркою. Одиночна гра — автознімком, не змінилась.

### Сторона vs власник (`Team`, `sim/PlayerRoster`) — з 2026-08-08

**`Team.forPlayer(playerId)` БІЛЬШЕ НЕМАЄ.** До матчів 5 на 5 сторона й номер
гравця були тим самим числом (гравець 0 — сині, гравець 1 — червоні), і
перетворення лежало розкидане по двадцяти файлах. Тепер:

- `Unit.team` — **сторона**: за нею рахуються бій, видимість, точки, перемога.
- `Unit.owner` — **номер гравця**, який командує. Союзник це `team == моя`,
  `owner != мій`: юніта видно як свого, наказу віддати не можна.
- `Team.byIndex(int)` / `Team.index()` — індекс САМОЇ сторони (0/1). Ним
  індексуються рахунок, втрати, утримані точки. Це НЕ playerId.
- `sim/PlayerRoster` — єдине місце, де playerId стає стороною. Незмінний склад
  матчу, будується зі слотів `StartMatch`; у checksum і знімок НЕ входить, бо
  однаковий у всіх за побудовою.
- Уся перевірка «чиє це військо» стоїть в ОДНОМУ місці —
  `UnitManager.collectOwned`, через яке проходять усі накази без винятку.
  Виділення (`trySelectAtPoint`, `selectInRect`) теж фільтрує за `owner`.
- Одиночна гра бере `PlayerRoster.local()` — рівно стара поведінка, тож SP не
  змінився ні на біт (перевірено запуском).

### Економіка й поповнення (`economy/`)
- `Economy` — золото на ГРАВЦЯ, а не на сторону. +5 за кожну точку СВОЄЇ команди
  раз на 5 с (`INCOME_PERIOD_TICKS`), і кожен гравець команди отримує ПОВНІ 5 —
  дохід не ділиться. Лічильник періоду один на матч.
- **Старт залежить від того, чи є стартова армія.** Одиночна гра: армія на полі
  + 100 золота (`STARTING_GOLD`). Мережевий матч: армії НЕМАЄ зовсім, натомість
  940 (`STARTING_GOLD_NO_ARMY`) — рівно вартість тієї самої армії (6 піхоти,
  3 кінноти, 2 гармати) плюс та сама сотня на перший хід. Прапорець
  `fieldStartingArmies` у `GameSimulation` мусить бути однаковий у всіх: від
  нього залежить і розстановка, і скарбниця.
- **Межа перемоги росте з розміром команди** (`VictoryTracker.TARGET_BASE` 900 +
  `TARGET_PER_EXTRA_PLAYER` 450 за кожного додаткового). Причина: дохід
  масштабується складом команди, а очки за точку — ні, тож при сталій межі матч
  5 на 5 вирішувався б рахунком ще до зустрічі армій. Число першого наближення,
  підбирати вимірюванням.
- `UnitType` — каталог замовлюваного: `INFANTRY` (50), `ARTILLERY` (150),
  розділи `INF`/`ART`. **Порядок констант — частина протоколу**: `SpawnCommand`
  везе `ordinal()`.
- `SpawnQueue` / `PendingSpawn` — замовлення живе 2 с (`HOLD_TICKS`) як
  напівпрозорий силует, і його можна зняти з поверненням золота. Далі юніт
  виходить із кута свого гравця (хост — лівий нижній, гість — правий верхній,
  `GameSimulation.SPAWN_MARGIN`) і йде в задану точку **з pathfinding**.
- Команди `SpawnCommand` / `CancelSpawnCommand`. Золото списується на тіку
  ВИКОНАННЯ, не при кліку. Усе входить у checksum (`C_ECONOMY`) і в знімок.
- UI: `screens/ui/CommandPanel` (scene2d на `hudStage`) — прибуток, золото,
  кнопка «ВІЙСЬКА» і прозоре меню розділів; `screens/renderer/SpawnGhostRenderer`
  — привид під курсором (екранні координати) і на місці висадки (світові).
- Кнопки «МЕНЮ» в лівому верхньому куті БІЛЬШЕ НЕМАЄ — там економіка. Паузу
  відкриває ESC; на мобільному вона зараз недоступна.
- **ПРОБІЛ — тактична пауза, тільки в одиночній грі** (`GameScreen.frozen`).
  Це НЕ те саме, що ESC: там меню й забране керування, тут симуляція завмирає, а
  камера, виділення й накази лишаються живими — пауза, щоб РОЗДИВИТИСЬ поле.
  Тому й окремий прапорець: один на два стани означав би або меню на пробіл, або
  втрату меню на ESC. При знятті обов'язковий `runner.resetClock()` — інакше час,
  що минув під паузою, стає пачкою тіків наздоганяння. У мережевому матчі клавіша
  мовчить: зупинити симуляцію в lockstep можна лише для себе.

### Супротивник-бот (`ai/`)
- **Бот — це ПІР, а не код симуляції.** `sim.tick()` цілочисельний і входить у
  checksum; евристика всередині нього мусила б уся лягти на `Fixed` і потрапити
  в хеш. Натомість `CommandContext` і без того єдиний канал зміни стану, тож бот
  сидить іззовні й віддає ті самі накази, що й людина. Усередині себе він
  вільний — float, колекції, будь-що: реплікується його ВИХІД, а не думка.
  Наслідок, який справдився: мережевий матч із ботом запрацював без переробок
  самого бота — знадобився лише його номер і місце, звідки шлються накази.
- `LocalMatchTransport(BotPlayer)` → `getPlayerIds()` стає `{0,1}`. Повідомлення
  бота народжується РАЗОМ із флешем локального гравця і на той самий тік. Це
  несуча деталь: `MatchRunner` чекає наказів від КОЖНОГО учасника, і тік без
  повідомлення від бота зупиняє матч намертво. Прив'язка до чужого флешу дає
  рівно одне повідомлення на тік без власного лічильника.
- **Бот НЕ шле checksum** — він не окрема симуляція. В одиночній грі це просто
  не запускає звірку (`ChecksumLedger:99-101`), а от у мережевому матчі мовчазний
  учасник вимкнув би її НАЗАВЖДИ — тому там діє окремий список
  `MatchRunner.checksumPlayers` (див. «Мережеві боти»). `prune` чистить за
  відсічкою тіку, тож витоку немає.
- **Зазирання немає.** Видимість рахується окремо для кожної сторони
  (`VisibilitySystem.update` проходить обох спостерігачів), тож
  `Unit.isVisibleTo(me)` — готова й чесна відповідь. Обійти туман війни означало
  б знецінити механіку, на якій тримається гра.
- `TacticalBrain` параметризований `playerId` — сторона це параметр, а не
  властивість класу. Інакше неможливий єдиний чесний тест рівнів: бот проти бота.
- **Три частоти** й причина в них одна: наказ СКИДАЄ те, що юніт робив. Наказ
  руху, повторений щочверть секунди, обнуляє маршрут і лишає роту тупцювати.
  Тому розподіл по точках — раз на 2 с, покупки — раз на 1 с, а бій хоч і
  переглядається щодумки, наказ віддає лише при ЗМІНІ цілі.
- **Ціль бою тримається (гістерезис), і без цього все інше не працює.** Ціль
  переобирається, лише коли стара мертва, невидима або вийшла з бою; склад
  шеренги можна переставити не частіше разу на 2 с. Раніше ціллю був найслабший
  ворог, а найслабший міняється щоразу, коли хтось дістав урон — HARD із
  періодом думки 2 тіки віддавав до 20 наказів атаки на секунду, кожен із яких
  скасовував попередній і перезапускав підхід. Армія перезапускала наступ
  швидше, ніж встигала зрушити; саме тому «найшвидший» рівень програвав
  найповільнішому.
- **Гармати НІКОЛИ не входять у групу наказу атаки.** `orderAttack` ставить їм
  `manualTarget`, а наступний же `marchArtillery` віддає наказ руху, який його
  стирає (`cancelAttackOrders`). Бот таким чином сам ганяв гармату між «іду на
  позицію» і «йду на ворога» кожні дві секунди.
- **Нічия точка пріоритетніша за чужу.** Спершу було навпаки — і два боти в
  дзеркальному матчі впирались один в одного, тримали по точці, а третю не брав
  ніхто: 290:290 усі п'ять хвилин, матч вирішувала анігіляція.
- **Збірний пункт і поріг маси — найважливіше в поведінці.** Підкріплення йде
  НЕ на ціль, а в тил (`RALLY_FRACTION` шляху від свого кута), і загін рушає,
  лише зібравши свій бюджет. Без цього при одній точці прибуток дає одного
  піхотинця на ~50 с, а йти йому 4–20 с — бот приходив по одному проти цілого
  загону й танув, скільки б не купував.
- **Відкат «іду → збираюсь» міряється ВИСНАЖЕННЯМ, а не купністю.** Рота на
  марші розтягується в колону сама собою; бот, який дивився на купність,
  розвертався на півдорозі збиратись, потім знову вперед — і так усю гру.
  Виміряно: у такому стані HARD програвав EASY.
- **Кілька напрямків одночасно — через БЮДЖЕТ, а не через рід військ.** Точки
  ранжуються (своя під зривом → нічия → чужа → своя спокійна), кожна дістає
  бюджет бійців, найближчі вільні роздаються згори вниз, а РЕЗЕРВ іде на
  найважчий напрямок — не на найпріоритетніший. Порожня точка без ворогів
  коштує гарнізону, спірна — не менше `massThreshold` і не менше, ніж
  `бачені вороги × attackOdds + 1`.
  - Попередник цього (`splitsForces`, відправляв на другу ціль УСЮ кінноту)
    виміряно програшним і **прибрано**: кіннота це 26 урону проти 15 у піхоти,
    забрати її з кулака означало програти головний бій.
  - **Вторинний напрямок відкривається лише на своїй половині шляху** і лише
    коли армії більше за `massThreshold + garrison`. Дрібний загін у чужому
    тилу йде наосліп (туман ховає те, що там стоїть, тож бюджет за баченими
    ворогами рахує нуль) і гине цілком: виміряно — HARD втрачав 7 із 13 юнітів
    за півтори хвилини й програвав EASY, який просто тримав усе купою.
- **Загін виходить із зони — і не отримує наказу повернутись. Це була головна
  вада.** У `march` умова «при ділі» була `contains(зона) АБО ближче за 120`, а
  `approachSpot` шукав найвище місце на кільці радіусом 70 БЕЗ перевірки, чи
  воно всередині чотирикутника. Для зони C на Жовтих Водах 5 із 8 кандидатів
  лежать поза зоною — і саме вони найвищі, бо високе тут навколо села, а не в
  ньому. Бот приходив, ставав поруч і не захоплював нічого до кінця матчу.
  Тепер кандидат мусить лежати В ЗОНІ, а «при ділі» = рівно `contains`.
- **«Я в бою» міряється дальністю ЮНІТА, а не `ENGAGE_RANGE`.** Ширший радіус
  блокував марш там, де наказу атаки ще немає (бракує переваги в головах), і
  загін завмирав за 240 одиниць від точки, яку мав узяти.
- **Рельєф у рішеннях (з 2026-08-05):** позиція в зоні зважує ярус ПЛЮС ліс
  (`usesCover`, ліс ≈ 0.8 ярусу — він дає ×1.5 захисту й маскування, але
  псує огляд); атака на вищий ярус коштує ×1.40 голів, на нижчий ×0.85
  (`TerrainCombatModifier` дає ±30% захисту, і бот раніше однаково охоче йшов
  угору й униз); гармата шукає позицію з ЛІНІЄЮ ЗОРУ на ціль і серед таких —
  найвищу, а ліс для неї штраф: гармата стріляє лише по тому, що бачить сама,
  тож схована гармата це 150 золота, які не стріляють.
- **Дистанція вогню — найдорожча навичка, і її не було зовсім (додано 2026-08-06).**
  `CombatManager.standoff` спиняє стрільця на `0.85 × дальність` = 76.5 для
  піхоти, а `processOrder` узагалі не зближується, якщо ціль уже в межах 90.
  `Infantry.hitChanceAt`: 100% до 30, 35% на 90 — тобто на 76.5 це ~50%, і той
  самий загін б'є ВДВІЧІ слабше. Гравець підводить лінію рукою, бот не робив
  цього ніколи. `TacticalBrain.pressRange` (рівні з `pressesRange`) раз на
  секунду веде вже задіяних стрільців на `PRESS_DIST` 26. Наказ саме РУХУ:
  дистанцію наказ атаки не приймає, а автоатака стріляє й на ходу. Кіннота під
  натиск не потрапляє за побудовою (дальність 20 < порогів).
- **Бот НЕ знає про роди військ (з 2026-08-06).** У ньому не лишилось жодного
  `instanceof` на тип юніта — було 27 місць. Знань там виявилось лише три, і
  всі три тепер живуть на самих юнітах, як `knockbackForce` і `usesRangedFx`:
  - `Unit.holdsLine()` — типово `damage > 0`. Гармата має 0 і в стрій не йде;
    цим замінено 20 перевірок (розподіл, маса, марш, оборона, охорона).
  - `Unit.outrunsLine()` — типово `швидкість > 30/с`, тобто між піхотою (20) і
    кіннотою (40). Ним визначається і хто відривається на марші, і кого слати
    на перехоплення.
  - `UnitType.share` — бажана частка складу. Частки ДОЗВОЛЕНИХ типів
    нормуються, тож рівень без артилерії сам розкидає її частку між рештою.
  - `Unit.type()` абстрактний навмисно: єдиний рядок, який новий юніт мусить
    написати заради бота, і забути про нього не дасть компілятор.

  **Новий рід військ = рядок у `UnitType` + клас + текстура.** Логіки бота —
  нуль, поки юніт вкладається в наявні ролі (лінійний / швидкий / підтримка).
  Справді нова роль (лікує, будує) потребуватиме коду в будь-якій архітектурі.

  Перевірено так: стенд детермінований, тож знято повний відбиток (переможець,
  причина, тривалість, рахунок, втрати, п'ять метрик поведінки) до й після.
  Матчі HARD/NORMAL збіглись ПОБАЙТОВО. Розійшлись лише матчі з EASY, і причина
  точна: стара формула рахувала частку кінноти як `1 − решта`, нова ділить
  `0.25/0.85` — різниця в один ULP, яка зрідка перемикає покупку. Переможці,
  рахунок і тривалість збіглись і там, ладдер лишився 10/12 · 10/12 · 9/12.
- **Кіннота не має відриватись від піхоти** (`holdsFormation`, важкий рівень).
  Хвиля виходить однією групою, але кіннота має швидкість 40 проти 20 — до цілі
  вона доходить УДВІЧІ раніше й зустрічає ворога сама. Поріг маси тут не рятує:
  він рахує, скільки вийшло, а не скільки дійшло разом. `holdBackHorse` дає
  відірваній кінноті за ціль не точку, а власну піхоту — але ЛИШЕ коли попереду
  справді юрба (ворогів біля позиції не менше, ніж самої кінноти). Безумовне
  вирівнювання виміряно дорогим: кіннота це темп усієї армії.
  - Це ЄДИНЕ місце, де бот наказує тому, хто вже йде. Марш рухомих не чіпає
    (повторний наказ скидає маршрут), і поки холдбек дивився лише на нерухомих,
    він не спрацьовував майже ніколи — відірвана кіннота саме в русі.
  - Числа: дуель лоб у лоб (одне сідло з прийомом, друге без, обидва сідла)
    7/12 проти 5/12; частка часу, який кіннота проводить під ворогом без своєї
    піхоти поруч, 50% → 30%.
  - **Чому лише важкому:** з прийомом в ОБОХ рівнів HARD проти NORMAL просів
    12/12 → 6/12 — темп втрачали обидва, і рівні зрівнялись. Як навичка важкого
    дає 10/12 і зберігає розрив.
- **Гармата ходила туди-сюди через КОНФЛІКТ ДВОХ КОНТРОЛЕРІВ.** `marchArtillery`
  женеться на позицію за 140 від точки, `protectGuns` бачить ворога ближче за
  своїх і відводить назад — і так кожні дві секунди. Оком це видно точно як
  «гармата дійшла до точки й повернулась». Тепер марш не чіпає гармату, поки
  діє її тривога (`gunAlarm`). Правило ширше за цей випадок: **два місця, що
  наказують одному юнітові, мусять мати явний пріоритет**.
- **Поріг першої хвилі — ПОВНИЙ бюджет, а не «скільки є»** (2026-08-06). Було
  `Math.min(want, size)`, і це знецінювало поріг маси саме там, де він потрібен:
  `budgetFor` проти роти на точці дає want 8, але якщо в загоні троє, `min`
  давав 3 — і трійка вирушала на вісьмох. Це та поведінка, яку видно оком:
  «бот іде кіннотою на А, де купа ворогів, і не звертає». Одна ця зміна дала
  HARD проти NORMAL **12/12** (було 7–10/12).
- **ВІДСТУПУ В БОТА НЕМАЄ, І ЦЕ ВИМІРЯНО.** Спокуса очевидна: програєш за
  головами — відійди. Пробували двічі (на збірний і коротким кроком 220):
  NORMAL із відступом програвав EASY 4/12 замість 9/12, хоча EASY відступати не
  вміє взагалі. Причина в правилах, а не в реалізації: РОЗРИВУ КОНТАКТУ в грі
  немає — той, хто відходить, не стріляє й отримує урон у спину, — а віддана
  точка це очки, тобто умова перемоги. Лікується не реакція, а ПРИБУТТЯ
  (поріг хвилі вище). Не повертати без механіки розриву контакту.
- **`underThreat` не міг справдитись НІКОЛИ — уся оборона точок була мертвим
  кодом** (знайдено й полагоджено 2026-08-06). Умова була
  `owner == me && holder == foe`, а `CaptureManager` при зриві лишає `holder`
  власником і тільки гасить `progress`; `holder` стає чужим рівно в той тік,
  коли `owner` обнуляється (`CaptureManager:118-122`). Два взаємно виключні
  стани. Тепер ознака — `owner == me && holder == me && progress < FULL`, тобто
  рівно те, що бачить гравець: смуга поповзла вниз. Наслідок був не
  теоретичний: `defendsPoints` ні на що не впливав, і бот не боронив нічого.
- **Оборонця не можна перепризначати щоцикла, і на швидких треба слати
  швидких.** Кіннота (40) заходить у тил, розподіл тягне туди піхоту (20),
  кіннота йде далі, наступний цикл тягне піхоту назад — кулак їздить по карті й
  не б'ється ніде. Тому `lockedTo`/`lockedUntil` (8 с) і `CAVALRY_DEFENCE_BONUS`
  у `assignObjectives`.
- **Гарнізон HARD піднято 2 → 3.** Двоє піхотинців програють чотирьом кіннотам
  за побудовою, тож гарнізон із двох означав точку, яку забирають безкоштовно.
  Виміряно: наліт на точки 8/12 → 4/12 і HARD проти NORMAL 7/12 → 10/12
  ОДНІЄЮ цією зміною.
- **Тривога за гарматою** (`protectGuns`): гармата має `damage = 0` і швидкість
  17 проти 40 у кінноти — відбитись і втекти вона не може НІЯК. Ознака тривоги —
  ПРОРИВ: ворог ближчий до гармати, ніж будь-хто зі своїх, і ближче за
  `GUN_ALARM` 140. Відповідь: гармата йде ДО СВОЇХ, двоє найближчих до
  нальотчика йдуть його бити й на 6 с випадають із маршу та бою.
  Радіус 220 замість 140 пробували — гірше в обох вимірах: тривога висить увесь
  бій (ворожа лінія завжди в межах 220), бот задкує гарматою й висмикує людей,
  і HARD програвав ЛЕГКОМУ рівню, який гармат не має взагалі.
- **Дзеркальний стенд симетричних вад НЕ БАЧИТЬ.** Цю коштувала 5 боїв із 6 і
  18 вцілілих проти 1 у дуелі 6×6, де єдина різниця — дистанція; у таблиці
  бот-проти-бота вона не проявлялась узагалі, бо косими були обидва. Для таких
  речей потрібен ЕКСПЛОЙТ-стенд: скриптований людський прийом проти бота,
  оцінка абсолютна. Зонд — це ПОВНОЦІННИЙ бот того ж рівня плюс один прийом,
  інакше міряється різниця в грі взагалі, а не прийом. Кожен прийом обов'язково
  з ГІСТЕРЕЗИСОМ: наліт без нього дав 0/12, з ним — 9/12, бо наказ, повторений
  щосекунди, щосекунди скидає підхід.

  | людський прийом | до правок | після |
  |---|---|---|
  | зійтись на дистанцію влучного вогню (дуель 6×6) | 5/6, 18 вцілілих проти 1 | навчений |
  | кіннотою на гармати | 9/12, бот втрачав УСІ гармати | 6/12 |
  | кіннотою забирати неприкриті точки | 11/12 | 4/12 |
  | сидіти в засідці в лісі | 1/12 — прийом виявився ПОГАНИМ | 3/12 |

  Засідка — приклад того, що гіпотезу треба міряти, а не впроваджувати: «бюджет
  рахується за видимими ворогами» звучить як діра, але сидіти в лісі коштує
  точок, і жодної фог-пам'яті боту через це НЕ додано.
- **Підкріплення йде хвилями до СВОГО ЗАГОНУ, а не на точку** (2026-08-06).
  Зобов'язання тепер на ЮНІТОВІ (`releasedFor`), а не на напрямку: `assignment`
  перескладається щодві секунди, і при прапорці на напрямку кожен новобранець
  одразу вважався «в поході» й ішов у зону сам — поріг маси гейтив рівно першу
  хвилю. Виміряно НЕЙТРАЛЬНИМ по перемогах (7/16 проти 9/16), лишено як
  правильніша модель. А от варіант «чекати на збірному» виміряно ГІРШИМ
  (6/16): поки поповнення стоїть у тилу, точки віддаються.
- **Гармату НЕ прив'язувати до центру маси піхоти.** Пробували 2026-08-06, щоб
  вона не виїжджала поперед строю: час «попереду» справді впав (.51→.44), але
  HARD проти NORMAL просів 8/12 → 6/12. Причина — наведення 3 с, яке скидає
  будь-який наказ руху, а позиція, прив'язана до строю, їздить за ним.
  Повертати лише разом із вирішеною проблемою наведення.
- `Difficulty` міняє ЛИШЕ якість рішень (період думання, резерв золота, поріг
  переваги для атаки, наявність гармат, чи читає рельєф, скільки напрямків).
  Ніяких бонусів до золота, урону чи огляду: перемога над ботом, який бачить
  крізь туман, нічого не означає. Вибір — `ScenarioScreen`, зберігається ІМЕНЕМ
  константи (`Settings.getBotDifficulty`), не ordinal: вставлений між наявними
  рівень тихо перемкнув би збережений вибір.
- **Числа рівнів підібрані ВИМІРЮВАННЯМ, не на око.** Стенд бот-проти-бота,
  по 4 сіда в обох сідлах = 8 матчів на конфігурацію, HARD проти NORMAL,
  один параметр за раз (2026-08-05):

  | зміна від базової | HARD виграв |
  |---|---|
  | `fronts` 3 (база) | 6–7/8 |
  | `fronts` 2 | 3–6/8 |
  | `fronts` 1 | **2/8** |
  | `massThreshold` 4 | 7/8 |
  | `massThreshold` 3 | **4/8** |
  | `massThreshold` 7 | **2/8** |
  | без `retreatsWounded` | **4/8** |
  | `attackOdds` 1.10 замість 1.00 | **3/8** |
  | `thinkPeriodTicks` 4 замість 2 | 6/8 |

  Висновки, які з коду не видно: більше напрямків СИЛЬНІШЕ (всупереч
  провалу `splitsForces` — бо ділиться чисельність, а не рід військ);
  поріг маси має вузьке дно 4–5; `retreatsWounded` тепер не нейтральний,
  а вигідний (раніше вимірювався 3/4 і туди, і сюди — його зробив вартим
  той факт, що загін більше не розпадається від наказів); поріг переваги
  вище паритету робить бота пасивним.
- `multiplayer` у `GameScreen` тепер = `transport != null`, а НЕ
  `playerIds.length > 1`: з ботом учасників теж двоє, але матч локальний, і
  паузу треба спиняти по-справжньому.
- **Пастка, вже набита:** `lastDecisionTick` не можна ініціалізувати
  `Integer.MIN_VALUE` — різниця `executeTick - lastDecisionTick` переповнюється
  в мінус, умова не спрацьовує ніколи, і бот мовчить увесь матч без єдиної
  ознаки поламаності.

### Дев-консоль (`debug/DevConsole`, `debug/DevView`)
Тильда (`~`) в матчі. **Створюється ТІЛЬКИ в одиночній грі** (`!multiplayer`):
майже все, що вона вміє, — пряма зміна стану повз накази або зміна темпу
годинника, і те, і те в lockstep розводить клієнтів на першому ж тіку.

- `aivsai [рівень] [рівень]` — обидві сторони під ботом. Окремого каналу не
  треба: `MatchRunner.issue` штампує накази ЛОКАЛЬНИМ playerId, тож мозок, чиї
  накази туди подають, стає гравцем за цим комп'ютером. Той самий прийом, яким
  бот тестується проти бота.
- `reveal on|off` — бачити всіх. **Тільки рендер.** Гейти видимості стоять у двох
  різних місцях: рендер (`UnitRenderer`, `Minimap`, `TerrainIndicatorRenderer` —
  усі через `DevView.visible`) і симуляція (`CombatManager`, `StateChecksum` —
  через `Unit.isVisibleTo` напряму). Чіпати можна ТІЛЬКИ перші, інакше
  спостереження змінює сам матч і побачене буде про іншу гру.
- `ai on|off` — наміри ботів на карті (`screens/renderer/AiIntentRenderer`):
  ціль, збірний пункт, суцільна лінія = йде / пунктир = збирається, підпис
  «рівень · стан · купа N/поріг · ціль». Без цього видно, ЩО бот робить, і не
  видно ЧОМУ — а всі знайдені в ньому вади були саме про «чому».
- `speed <0.25..8>` — множить лише `delta` для `runner.update`; крок тіку
  лишається 25 мс, тобто симуляція не міняється, просто тіків за секунду більше.
- `win <p>` реалізовано через знищення армії суперника, а НЕ через запис у
  `VictoryTracker`: так спрацьовує та сама умова, що в справжньому матчі, разом
  із підсумковими числами. Прямий запис показав би екран, якого гра не вміє
  виробляти.
- `spawn` спершу повертає ціну через `Economy.refund`, потім кличе
  `sim.spawnUnit` — той списує золото, і без цього консольний спавн тихо їв би
  скарбницю.
- `pause on|off` — та сама тактична пауза, що й пробіл; нею спиняють матч ботів,
  щоб роздивитись позицію.
- **`debug/DownloadsGag` — ТИМЧАСОВИЙ жарт** (найсвіжіша картинка з Завантажень
  на `aivsai`, на прохання 2026-08-05, «потім заберемо»). Прибирається одним
  файлом плюс поле `gag` і виклик у `DevHost.setAutoPlay`; більше від нього
  нічого не залежить.
- `-Dlb.devCmd="aivsai hard hard;reveal on;ai on;speed 4;console on"` — сценарій
  на старті, розділювач `;`. Без нього консоль неможливо ні зняти автознімком,
  ні прогнати без людини за клавіатурою.
- `DevView` — статичні поля, і це свідомо: читачі це окремі рендерери, створені
  в різних місцях; тягнути посилання через п'ять конструкторів заради двох
  прапорців було б гірше. `GameScreen.dispose` кличе `DevView.reset()` —
  інакше ввімкнений `reveal` пережив би вихід у меню.

### Умова перемоги (`sim/VictoryTracker`)
- Дві умови. **Очки**: раз на 5 секунд (`SCORE_PERIOD_TICKS`) кожна сторона
  отримує `POINTS_PER_CAPTURE` (5) за кожну утримувану точку — та сама
  швидкість «очко за точку за секунду», але одним видимим кроком, а не
  цоканням секундоміра; хто перший набрав `TARGET` (900) —
  виграв. На 3 точках це 5 хв при повному контролі, 15 хв при одній точці.
  **Анігіляція**: сторона програє, коли в неї НЕМАЄ ні живих юнітів, ні
  замовлень у черзі, ні золота на найдешевшого юніта (ціна береться з
  `UnitType`, не константою). Усі три умови разом — по одній кожна дає хибну
  поразку, поки рота ще виходить із кута.
- Обидві перевірки — раз на період, не щотіку: анігіляція проходить по всіх
  юнітах. Викликається ОСТАННІМ у `GameSimulation.tick()`, після точок і
  економіки.
- **Симуляція після перемоги НЕ зупиняється.** У lockstep розбіжність у тому,
  чи виконався тік, — миттєвий десинк. Результат лише фіксується, показує
  його і глушить ввід виключно `GameScreen`.
- Нічия можлива: обидва перетнули `TARGET` на одному нарахуванні з рівним
  рахунком, або обидва анігільовані. `isDraw()` = `finished && winner == null`.
- Стан симуляції: checksum-компонент `C_VICTORY` і блок у `SimulationSnapshot`.
- UI: рахунок — `scoreSelfLabel`/`scoreFoeLabel` у `GameScreen`, ВЕРХ ПО ЦЕНТРУ
  `hudStage` впритул до межі екрана (`padTop 2`). Обидва числа ЗОЛОТІ
  (`COLOR_ACCENT`); свої перші. Синьо-червоні цифри пробували 2026-08-04 і
  відкинули — вибивались зі спокійної золотої гами HUD. Кольори сторін
  (`UIFactory.COLOR_TEAM_SELF/FOE`) лишились там, де справді розрізняють:
  на літерах точок і на зонах. Під числами ряд літер (`pointTags`): колір = хто тягне,
  сіра = нічия, мигання = зараз захоплюють. Літера НЕ рухається ніколи —
  групування «свої ліворуч, чужі праворуч» відкинуте саме тому, що змусило б
  її стрибати в мить захоплення. Там же тягнеться `waitLabel`, тому рознесені
  по `padTop` (2 проти 66) — інакше підказка лягає на цифри. У `CommandPanel`
  рахунку НЕМАЄ навмисно: та панель про золото й замовлення.
- **Підсумок матчу** знімається ОДИН раз, у `finish()`: `lost[2]` (втрачено
  юнітів) і `ownedAtEnd[2]` (утримувано точок). Знищено = втрати суперника, у
  1v1 окремого поля не треба. Тривалість — із `decidedTick`.
  Лічильника, що тікає на кожній смерті, тут НЕМАЄ навмисно: місць загибелі
  три (`takeDamage`, `takeDamageWithTerrain`, `GameSimulation.removeArmy`), і
  кожне нове стало б четвертим, про яке забули. Скан працює тому, що `allUnits`
  під час матчу НЕ чиститься (мертві лишаються з `alive == false`), а знімок
  пише всіх юнітів без фільтра — тож і ресинк історію втрат не з'їдає.
  `ownedAtEnd` саме ЗБЕРІГАЄТЬСЯ, а не читається під час показу: симуляція
  після перемоги не спиняється, і живий `countOwned` показував би, як підсумок
  повзе вже після кінця матчу.

### Екран результату (`screens/game/MatchResultOverlay`)
- **Вигляд і тайминги описані в [`DESIGN.md`](DESIGN.md) §9** — читай перед
  будь-якою правкою. Там же єдиний у грі дозвіл на помітну анімацію і межі
  того, що взагалі можна анімувати всередині `Table`.
- Смуга на всю ширину поверх затемненого поля, а НЕ панель: поле бою лишається
  видимим над і під нею.
- Показується через **1.2 с** після `isFinished()` (`GameScreen.RESULT_DELAY`),
  але ввід глушиться НЕГАЙНО (`GameScreen.inputSealed()` — ширше за
  `modalActive()` рівно на цю паузу). Ловець вводу мусить ПОГЛИНАТИ подію:
  порожня `modalStage` повертає `false`, і наказ провалився б далі по
  мультиплексору, поки вікна ще немає.
- `MatchNoticeOverlay` лишився ТІЛЬКИ обриву зв'язку. Раніше він показував і
  результат («стан однаковий»), але обрив — аварія, а кінець матчу — подія,
  заради якої гравець грав, і одного тону на двох замало.
- Вихід суперника теж іде сюди (`isAlone()` спрацьовує швидше за анігіляцію),
  але з `statsKnown = false`: `VictoryTracker` ще не знімав підсумок, і нулі
  замість чисел були б брехнею.
- В інтерфейсі — **«стратегічні точки», ніколи «села»**: село це те, як точка
  намальована на Жовтих Водах, а не те, чим вона буде на наступній карті.

### Масштабування інтерфейсу (`ui/UIScale`, `ui/ScreenResolution`)
- `UIScale.forHeight(h)` = `clamp(snap(h/720, 0.25), 0.75, 2.0)` — ОДИН множник на
  весь HUD. Стеля 2.0× — це запас різкості шрифту: `UIFactory.generateTintableFont`
  пече гліфи вдвічі більшими й малює з `setScale(0.5f)`.
- Три сцени матчу (`hudStage`, `pauseStage`, `modalStage`) — `ScreenViewport` із
  `setUnitsPerPixel(1/scale)`. Ставити множник ТРЕБА до `viewport.update(...)`.
- **HUD живе в логічних одиницях, ввід — у фізичних пікселях.** Усе, що перевіряє
  влучання по намальованому вручну HUD (`Minimap`, `SelectionPanel`), зобов'язане
  пройти через `UIScale.inputXToLogical` / `inputYToLogical`. Голого
  `Gdx.graphics.getHeight() - sy` в `GameScreen` більше немає — не повертати.
- `GameScreen.layoutHud()` рахує розкладку на початку кадру: мінікарта задає
  `frameWidth()`, під нього тиснеться `SelectionPanel.layout(...)`. Малювання й
  перевірка влучання читають ті самі числа.
- **Площа видимого світу стала.** `camera.zoom = userZoom × aspectFit()`, де
  `aspectFit = sqrt(900×580 / (worldW×worldH))`. У `camera.zoom` НЕ пишуть напряму —
  тільки `setZoom` (ефективний масштаб) або `setUserZoom`. Без цього гравець на
  21:9 бачив на 34% більше карти, ніж гравець у вікні.
- **Камера обмежується по ЦЕНТРУ** (`clamp(position, 0, mapWidth/Height)` у
  `handleCameraMovement`), тобто їй свідомо дозволено визирати за межі карти —
  збоку видно чорноту. Клемп по КРАЮ (`clamp(x, halfW, mapWidth − halfW)`)
  пробували 2026-08-04 і **відкинули**: він прибирає чорноту, але не пускає
  погляд за периметр узагалі, і керування стає тісним. Не повертати без
  прямого прохання. Саме тому `CommandPanel` має власну чорну плашку — вона
  лежить на межі кадру й не може розраховувати на карту під собою.
- Вікно нерозтяжне (`setResizable(false)`); розмір міняє лише список пресетів у
  налаштуваннях. Роздільність і повний екран лежать у `LostBatalion.Settings`,
  відновлює їх `LostBatalion.create()` — у лаунчері `Preferences` ще не існує.
- Зміна режиму з обробника scene2d — ТІЛЬКИ через `Gdx.app.postRunnable`:
  `BaseScreen.resize` перескладає сцену, тобто звільняє кнопку, всередині
  обробника якої ти стоїш.

## Current state / known gaps (as of this doc)

Implemented: unit selection & movement, formations (line + curved), terrain
movement/combat/visibility modifiers, fog of war, infantry auto/ordered combat,
artillery AoE strikes, mobile controls, main menu / scenario / settings screens,
pause overlay.

Not yet implemented (despite the design brief mentioning them):
- **No base building.** Економіка є (золото з точок захоплення + замовлення
  військ), але видобутку ресурсів і будівництва немає.
- **Бот ще НЕ доведений — робота триває з 2026-08-06.** Дві вади, які видно
  оком і яких не показала таблиця перемог:
  - **Гармати й кіннота йдуть на точку ПО ОДНОМУ під вогонь.** Поріг маси
    гейтить лише першу хвилю. `marchArtillery` — окремий шлях, він не питає
    `committedTo` взагалі. А `march` збирає групу тільки з тих, хто `!isMoving`,
    і оскільки `committedTo` вже стоїть, кожне наступне поповнення, дійшовши до
    збірного пункту, вирушає далі САМЕ, групою з одного. Той самий струмочок,
    заради якого поріг маси і робився, зайшов з іншого боку.
  - **Велика армія (спробувати з ~10000 золота) збивається в купу і застрягає
    сама в собі.** Не відтворено й не виміряно. Куди дивитись: `UnitSeparation`
    O(n²) з половинним відштовхуванням і порогом `MIN_PUSH` (його ж коментар
    каже, що на сотнях юнітів потрібна сітка сусідства); `SpawnQueue` висаджує
    всі покупки в одну точку; а юніт, який стоїть, наказу більше не отримує,
    тож розчепити купу нема чому.
- **Enemy AI Є** (`ai/`, з 2026-08-05) — бот замовляє війська, бере точки,
  б'ється, має три рівні, веде кілька напрямків і читає рельєф у чотирьох
  місцях: позиція в зоні (висота + ліс), поріг атаки вгору/вниз, вогнева
  позиція гармати з перевіркою лінії огляду, обхід річки. Чого ще немає:
  реакції на СКЛАД армії суперника (кіннота проти гармат тощо), засідок у лісі
  як окремого прийому, і шляху через ліс/річку як свідомого вибору — річка
  відкидається тільки як кінцева точка.
- **Win/lose conditions Є** (`sim/VictoryTracker`, див. вище) — очки за точки
  плюс анігіляція. Інших цілей і сценарних завдань немає.
- **Pathfinding Є** (`path/NavGrid` + `path/PathFinder`, A* цілочисельний і
  детермінований), але ТІЛЬКИ по статичній місцевості: юніти в сітці не
  враховані, локального уникнення зіткнень і рознесення груп немає.
- **No tests** у репозиторії (`src/test` відсутній у всіх модулях). Прогонні
  харнеси пишуться в scratchpad сесії й не зберігаються.
- **Симуляцію НЕ можна підняти без графіки** — і це заважає перевіркам:
  `CombatManager` створює `TargetPopupManager`, який вантажить текстуру через
  `Gdx.files`, тож `new GameSimulation(...)` падає з NPE поза грою. Мережевий
  ШАР при цьому від libGDX не залежить навмисно (`NetLog` це береже), і стенд
  лоббі headless працює повністю. Розв'язати цю пару варто окремо: тоді стане
  можливим стенд «два клієнти → матч → checksum» без вікна.
- Only one scenario/map. `server` module is an unused stub.
- Some debug `Gdx.app.log` calls in the combat/unit hot path (`Unit.update`,
  `CombatManager.tryAttack`) at LOG_DEBUG.

## Conventions / gotchas

- Dispose everything: subsystems own their `SpriteBatch`/`ShapeRenderer`/
  `Texture`/`Pixmap` and dispose in `dispose()`. Follow the pattern for new ones.
- Terrain masks sampled with **Y flipped**; world Y is up, pixmap Y is down.
- Artillery is deliberately excluded from the normal `attack()` / order pipeline
  — guard new combat code with `instanceof Artillery` checks like existing code.
- Видимість гейтить і рендер, і прицілювання — але це ДВА різні набори місць.
  Рендер ходить через `DevView.visible`, симуляція (`CombatManager`,
  `StateChecksum`) — через `Unit.isVisibleTo` напряму. Новий код мусить питати
  той шлях, до якого належить; переплутати їх означає або зробити налагоджувальний
  режим таким, що змінює матч, або лишити його без дії.
- **Опитуваний ввід мультиплексор НЕ гасить.** `Gdx.input.isKeyPressed` і
  `isButtonPressed` питають стан клавіші напряму й нічого не знають про те, хто
  поглинув подію. Через це WASD їздив камерою з відкритою консоллю. Усе, що
  опитується (`handleCameraMovement`, ALT-оверлей, малювання кривої), мусить
  саме питати `devOpen()`/`paused`. Правило для будь-якого нового опитування.
- **`keyDown` і `keyTyped` — дві події однієї клавіші.** Поглинути першу
  недосить: друга прийде з символом. Саме так тильда вписувала себе в поле
  консолі, яке щойно відкрила. Клавіші-перемикачі мусять гасити й `keyTyped`.
- Comments/log tags often Ukrainian (`COMBAT`, `UNIT`). Keep consistent.
